## 1. Overview and Responsibilities

The Stage Splitter takes a Calcite `RelNode` tree (the logical query plan produced by the planner) and decomposes it into a directed acyclic graph (DAG) of **stages**. Each stage is a self-contained SQL string (generated by `SqlProducer`) that can be executed independently on a single worker node or a set of worker nodes reading the same partition. Stages communicate through **exchanges** (also called shuffles), which are the only mechanism for data movement between machines.

### Inputs

| Input | Source | Description |
|---|---|---|
| `RelNode` | Query Planner (Calcite) | A fully-resolved Calcite RelNode tree **(logical)** — root relation + schema; no physical execution details |
| `CatalogStats` | Catalog / Statistics Store | Table row counts, sizes, column cardinalities used for cost-based decisions |

### Outputs

| Output | Consumer | Description |
|---|---|---|
| `ExecutionDAG` | Distributed Scheduler | A DAG of `Stage` objects connected by `ExchangeEdge` objects |

### Responsibilities

1. **Tree traversal** — walk the Calcite RelNode tree bottom-up, identifying every point where data must cross a machine boundary.
2. **Exchange insertion** — apply rule-based and cost-based logic to decide the exchange type (HASH, BROADCAST, GATHER, ROUND_ROBIN) at each boundary.
3. **Plan surgery** — cut the RelNode tree at each exchange boundary, producing self-contained sub-trees; generate SQL per stage via `SqlProducer`, replacing cross-stage references with placeholder table references (e.g., `shuffle_input_N`).
4. **Partial aggregation push-down** — when a `LogicalAggregate` triggers a HASH exchange, manually decompose aggregations (e.g., `SUM(x)` → partial: `SUM(x) AS partial_sum`, final: `SUM(partial_sum)`) and generate separate SQL for each phase.
5. **Redundant exchange elimination** — if data is already partitioned on the required key(s), suppress the exchange.
6. **DAG construction** — assemble the `ExecutionDAG` with correct dependency edges and stage metadata.

### Position in the System

```
Query Planner  -->  [Stage Splitter]  -->  ExecutionDAG  -->  Distributed Scheduler
                          ^
                    CatalogStats
```

## Updated Pipeline Context

The Calcite RelNode tree received by the Stage Splitter is a **logical plan**, not a physical one. Understanding where this plan comes from — and where it goes — clarifies the Stage Splitter's role and responsibilities.

### How the Plan Arrives

```
SQL / PPL
    |
    v
UnifiedQueryPlanner
    |
    v
Calcite RelNode  (logical relational algebra)  ← this is what the Stage Splitter receives
```

The RelNode tree encodes **what** to compute (projections, filters, joins, aggregations) using standard relational operators. It does not specify **how** those operators execute — there are no choices of join algorithm, parallelism degree, or memory layout at this stage.

### What the Stage Splitter Does (and Does Not Do)

The Stage Splitter works entirely on the logical Calcite RelNode tree. It does not need to know about physical execution details. Its sole concern is **where data must move** across machine boundaries:

- It identifies points in the logical plan where a data exchange (shuffle) is required.
- It inserts exchange boundaries and splits the tree into self-contained stage sub-trees.
- For each stage sub-tree, `SqlProducer.toSql()` generates a SQL string that DataFusion parses natively.

### What Happens After Splitting

Once the Stage Splitter produces the `ExecutionDAG`, each stage's SQL string is dispatched to DataFusion workers. DataFusion parses the SQL via `SessionContext::sql()`, producing a logical plan, and then translates it into its own **physical plan**, making decisions such as:

- Which join algorithm to use (hash join, merge join, nested-loop join).
- How many threads to use (intra-stage parallelism).
- Memory buffer sizing and spill strategies.

### Separation of Concerns

| Concern | Owner |
|---|---|
| WHERE data moves (exchange boundaries, shuffle strategy) | Stage Splitter |
| HOW operators execute (join algorithm, parallelism, memory) | DataFusion (per-stage) |

This separation keeps the Stage Splitter focused on distribution topology and leaves physical execution decisions to the engine that will actually run each fragment.

## 2. Java Interfaces and Data Structures

### 2.1 StageSplitter

```java
package org.opensearch.lakehouse.splitter;

import org.apache.calcite.rel.RelNode;

/**
 * Entry point for decomposing a Calcite RelNode tree into an execution DAG.
 * Implementations must be stateless and thread-safe.
 */
public interface StageSplitter {

    /**
     * Split a Calcite RelNode tree into a DAG of executable stages.
     * Each stage contains a SQL string generated by SqlProducer.
     *
     * @param plan          The complete, resolved Calcite RelNode tree.
     * @param catalogStats  Statistics provider for tables referenced in the plan.
     * @return              An ExecutionDAG whose stages are topologically ordered
     *                      such that all producers precede their consumers.
     * @throws StageSplitterException if the plan contains unsupported constructs
     *                                or a cycle is detected.
     */
    ExecutionDAG split(RelNode plan, CatalogStats catalogStats);
}
```

### 2.2 ExecutionDAG

```java
package org.opensearch.lakehouse.splitter;

import java.util.List;
import java.util.Map;

/**
 * Immutable directed acyclic graph of execution stages.
 * Edges represent data flow from producer stage to consumer stage via an exchange.
 */
public interface ExecutionDAG {

    /**
     * All stages in this DAG, keyed by stageId.
     * Guaranteed to be non-empty.
     */
    Map<String, Stage> stages();

    /**
     * All exchange edges in the DAG.
     * An edge (A -> B) means stage B consumes the output of stage A
     * through the described exchange.
     */
    List<ExchangeEdge> edges();

    /**
     * The stageId of the final (root) stage whose output is the query result.
     * This stage has no outgoing edges.
     */
    String rootStageId();

    /**
     * Return stages in topological order: producers before consumers.
     * Useful for the scheduler to launch stages in dependency order.
     */
    List<Stage> getTopologicalOrder();

    /**
     * Return the direct upstream dependencies (input stages) of the given stage.
     *
     * @param stageId  The stage whose dependencies are requested.
     * @return         List of stages that must complete before stageId can start.
     *                 Empty list for leaf (scan) stages.
     */
    List<Stage> getDependencies(String stageId);
}
```

### 2.3 Stage

```java

 * A single unit of distributed execution: a self-contained SQL string

     * Stable, unique identifier for this stage within the query.

     * Estimated output size in bytes. Used for broadcast threshold decisions

     */
    long estimatedBytes();
```

### 2.5 ExchangeType Enum

```java
package org.opensearch.lakehouse.splitter;

/**
 * Describes the data routing strategy for an exchange between two stages.
 */
public enum ExchangeType {

    /**
     * Rows are routed to partitions by hashing one or more key columns.
     * All rows with the same hash land on the same worker.
     * Used for: joins on join keys, grouped aggregations on grouping keys,
     *           UNION DISTINCT (hash on all columns).
     */
    HASH,

    /**
     * The entire dataset is replicated to every worker in the consumer stage.
     * Used when one side of a join is small enough that replication is cheaper
     * than a full hash shuffle on the large side.
     */
    BROADCAST,

    /**
     * All rows are funneled to a single worker (the coordinator or one designated
     * worker). Used for ORDER BY ... LIMIT at the top of the plan where a global
     * sort is required.
     */
    GATHER,

    /**
     * Rows are distributed to consumer workers in round-robin order with no
     * partitioning guarantee. Used for UNION ALL where ordering/grouping is
     * not required.
     */
    ROUND_ROBIN
}
```

### 2.6 ExchangeSpec

```java
package org.opensearch.lakehouse.splitter;

import java.util.List;

/**
 * Complete specification for a single exchange (shuffle) between two stages.
 */
public interface ExchangeSpec {

    /**
     * The routing strategy for this exchange.
     */
    ExchangeType type();

    /**
     * For HASH exchanges: zero-based indices of the output columns of the
     * source stage that form the partition key. Order matters for composite keys.
     * Empty for BROADCAST, GATHER, and ROUND_ROBIN exchanges.
     */
    List<Integer> partitionColumnIndices();

    /**
     * For HASH and ROUND_ROBIN exchanges: the number of output partitions
     * (== the parallelism of the consumer stage). Typically equals the number
     * of worker nodes available for the consumer stage.
     * For BROADCAST: ignored (consumer parallelism is handled by the scheduler).
     * For GATHER: always 1.
     */
    int numPartitions();

    /**
     * For BROADCAST decisions: the estimated size of the broadcast side in bytes.
     * If this exceeds the configured broadcastThresholdBytes at planning time,
     * the splitter falls back to HASH exchange instead.
     * 0 for non-broadcast exchanges.
     */
    long broadcastThresholdBytes();
}
```

## 3. Splitting Algorithm

### 3.1 High-Level Flow

```
split(plan, stats):
    context = new SplitContext(stats)
    visitedRoot = walkBottomUp(plan.rootRelation, context)
    dag = context.buildDAG(visitedRoot)
    return dag
```

The core of the algorithm is a bottom-up recursive walk of the Calcite RelNode tree. At each node the visitor:

1. Recursively processes all child relations first.
2. Applies exchange insertion rules for the current node type.
3. If an exchange is needed, creates a new stage boundary: the current subtree becomes a new stage (SQL generated via `SqlProducer`), and the parent will consume it via a placeholder `LogicalTableScan` referencing a shuffle input table.

### 3.2 SplitContext

```java
class SplitContext {
    CatalogStats stats;
    List<Stage> completedStages = new ArrayList<>();
    List<ExchangeEdge> edges = new ArrayList<>();
    int stageCounter = 0;
    long broadcastThresholdBytes;   // default: 10 * 1024 * 1024 (10 MB)

    String nextStageId() { return "stage-" + (stageCounter++); }
}
```

### 3.3 Bottom-Up Walk with Exchange Insertion Rules

```
function walkBottomUp(rel, context) -> StageFragment:
    // 1. Recurse into children first
    children = []
    for each input in rel.inputs:
        childFragment = walkBottomUp(input, context)
        children.add(childFragment)

    // 2. Apply exchange insertion rules based on current rel type
    switch rel.type:

        case LogicalTableScan:
            // Leaf node. No exchange needed; becomes a scan stage.
            return StageFragment(rel, partitioningInfo=UNPARTITIONED)

        case LogicalFilter, LogicalProject:
            // Pass-through: inherit child's partitioning unchanged.
            rel.input = children[0].rootRel
            return StageFragment(rel, partitioningInfo=children[0].partitioningInfo)

        case LogicalAggregate:
            return handleAggregate(rel, children[0], context)

        case LogicalJoin:
            return handleJoin(rel, children[0], children[1], context)

        case LogicalSort:
            return handleSort(rel, children[0], context)

        case LogicalSort (LIMIT only, no ORDER BY):
            // Usually paired with SORT; handled by handleSort peeking at parent.
            // On its own, a LIMIT over an already-gathered stream needs no exchange.
            return StageFragment(rel, partitioningInfo=children[0].partitioningInfo)

        case LogicalUnion:
            return handleSet(rel, children, context)

        case LogicalWindow:
            return handleWindow(rel, children[0], context)

        default:
            // Unknown rel: pass through, inherit first child partitioning.
            return StageFragment(rel, partitioningInfo=children[0].partitioningInfo)
```

### 3.4 Rule: LogicalAggregate

```
function handleAggregate(aggRel, childFragment, context) -> StageFragment:

    groupingKeys = aggRel.groupings  // list of column references

    if groupingKeys is empty:
        // Global aggregate (COUNT(*), SUM without GROUP BY).
        // Need all rows on one worker -> GATHER exchange.
        spec = ExchangeSpec(GATHER, [], numPartitions=1, broadcastThresholdBytes=0)
        exchangedFragment = insertExchange(childFragment, spec, context)
        aggRel.input = exchangedFragment.placeholderReadRel
        return StageFragment(aggRel, partitioningInfo=SINGLE_PARTITION)

    else:
        // Grouped aggregate. Apply partial aggregation optimization (see Section 5).
        // Step 1: Push partial aggregate BEFORE the exchange.
        partialAgg = buildPartialAggregate(aggRel, childFragment.rootRel)

        // Step 2: Insert HASH exchange on grouping key columns.
        keyIndices = resolveColumnIndices(groupingKeys, childFragment.outputSchema)
        spec = ExchangeSpec(
            HASH,
            partitionColumnIndices = keyIndices,
            numPartitions = context.workerCount,
            broadcastThresholdBytes = 0
        )
        partialFragment = StageFragment(partialAgg, partitioningInfo=HASH_ON(keyIndices))

        // Check for redundant exchange.
        if childFragment.partitioningInfo == HASH_ON(keyIndices):
            // Data already hash-partitioned on the grouping keys.
            // Skip the exchange; run final aggregate directly.
            aggRel.input = childFragment.rootRel
            return StageFragment(aggRel, partitioningInfo=HASH_ON(keyIndices))

        exchangedFragment = insertExchange(partialFragment, spec, context)

        // Step 3: Final aggregate runs in the consumer stage on pre-aggregated data.
        finalAgg = buildFinalAggregate(aggRel, exchangedFragment.placeholderReadRel)
        return StageFragment(finalAgg, partitioningInfo=HASH_ON(keyIndices))
```

### 3.5 Rule: LogicalJoin

```
function handleJoin(joinRel, leftFragment, rightFragment, context) -> StageFragment:

    leftKeys  = extractJoinKeys(joinRel, side=LEFT)   // column indices in left output
    rightKeys = extractJoinKeys(joinRel, side=RIGHT)  // column indices in right output

    leftEstBytes  = estimateBytes(leftFragment, context.stats)
    rightEstBytes = estimateBytes(rightFragment, context.stats)

    threshold = context.broadcastThresholdBytes  // default 10 MB

    // --- Broadcast join ---
    if rightEstBytes <= threshold:
        // Broadcast the right (build) side to every worker; left side stays local.
        broadcastSpec = ExchangeSpec(BROADCAST, [], numPartitions=context.workerCount, broadcastThresholdBytes=rightEstBytes)
        rightExchanged = insertExchange(rightFragment, broadcastSpec, context)
        joinRel.left  = leftFragment.rootRel          // no exchange on probe side
        joinRel.right = rightExchanged.placeholderReadRel
        return StageFragment(joinRel, partitioningInfo=leftFragment.partitioningInfo)

    else if leftEstBytes <= threshold:
        // Broadcast the left (build) side.
        broadcastSpec = ExchangeSpec(BROADCAST, [], numPartitions=context.workerCount, broadcastThresholdBytes=leftEstBytes)
        leftExchanged = insertExchange(leftFragment, broadcastSpec, context)
        joinRel.left  = leftExchanged.placeholderReadRel
        joinRel.right = rightFragment.rootRel
        return StageFragment(joinRel, partitioningInfo=rightFragment.partitioningInfo)

    // --- Hash join (both sides shuffled) ---
    else:
        // Hash-shuffle both sides on their respective join keys.
        // Both sides must use the same numPartitions so matching keys land together.
        numPartitions = context.workerCount

        leftSpec = ExchangeSpec(HASH, leftKeys, numPartitions, 0)
        rightSpec = ExchangeSpec(HASH, rightKeys, numPartitions, 0)

        // Avoid redundant exchange if a side is already correctly partitioned.
        if leftFragment.partitioningInfo != HASH_ON(leftKeys):
            leftExchanged = insertExchange(leftFragment, leftSpec, context)
        else:
            leftExchanged = leftFragment

        if rightFragment.partitioningInfo != HASH_ON(rightKeys):
            rightExchanged = insertExchange(rightFragment, rightSpec, context)
        else:
            rightExchanged = rightFragment

        joinRel.left  = leftExchanged.rootRel
        joinRel.right = rightExchanged.rootRel
        return StageFragment(joinRel, partitioningInfo=HASH_ON(leftKeys))
```

### 3.6 Rule: LogicalSort (with optional LIMIT)

```
function handleSort(sortRel, childFragment, context) -> StageFragment:

    parent = sortRel.parent  // peek at parent node

    if parent is FETCH_REL (i.e., ORDER BY ... LIMIT N):
        // Top-K query. Need a global merge on one node.
        // Insert GATHER exchange so one worker does the final merge + limit.
        spec = ExchangeSpec(GATHER, [], numPartitions=1, 0)
        exchangedFragment = insertExchange(childFragment, spec, context)
        sortRel.input = exchangedFragment.placeholderReadRel
        return StageFragment(sortRel, partitioningInfo=SINGLE_PARTITION)

    else if isTotalOrderRequired(sortRel):
        // Plain ORDER BY without LIMIT: must gather all rows to sort globally.
        spec = ExchangeSpec(GATHER, [], numPartitions=1, 0)
        exchangedFragment = insertExchange(childFragment, spec, context)
        sortRel.input = exchangedFragment.placeholderReadRel
        return StageFragment(sortRel, partitioningInfo=SINGLE_PARTITION)

    else:
        // Sort within each partition (e.g., ORDER BY on an already-partitioned key).
        // No exchange needed.
        sortRel.input = childFragment.rootRel
        return StageFragment(sortRel, partitioningInfo=childFragment.partitioningInfo)
```

### 3.7 Rule: LogicalUnion

```
function handleSet(setRel, childFragments, context) -> StageFragment:

    switch setRel.setOp:

        case UNION_ALL:
            // UNION ALL just concatenates; no grouping/deduplication needed.
            // Use ROUND_ROBIN to distribute rows evenly across workers,
            // or simply chain the fragments if all are already in parallel.
            spec = ExchangeSpec(ROUND_ROBIN, [], numPartitions=context.workerCount, 0)
            exchangedFragments = []
            for each childFragment in childFragments:
                exchangedFragments.add(insertExchange(childFragment, spec, context))
            // The consumer stage merges streams from all upstream stages.
            setRel.inputs = [ef.placeholderReadRel for ef in exchangedFragments]
            return StageFragment(setRel, partitioningInfo=UNPARTITIONED)

        case UNION_DISTINCT:
            // Must deduplicate. Hash on all output columns.
            allColumnIndices = [0 .. setRel.outputSchema.columnCount - 1]
            spec = ExchangeSpec(HASH, allColumnIndices, context.workerCount, 0)
            exchangedFragments = []
            for each childFragment in childFragments:
                exchangedFragments.add(insertExchange(childFragment, spec, context))
            setRel.inputs = [ef.placeholderReadRel for ef in exchangedFragments]
            return StageFragment(setRel, partitioningInfo=HASH_ON(allColumnIndices))

        case INTERSECT, EXCEPT:
            // Similar to UNION DISTINCT; hash on all output columns.
            // (same logic as UNION_DISTINCT above)
            ...
```

### 3.8 insertExchange Helper

```
function insertExchange(sourceFragment, spec, context) -> StageFragment:

    // 1. Seal sourceFragment as a completed stage.
    stageId = context.nextStageId()
    stage = new StageImpl(
        stageId       = stageId,
        fragment      = sourceFragment.rootRel,
        outputExchange= spec,
        estimatedRows = sourceFragment.estimatedRows,
        estimatedBytes= sourceFragment.estimatedBytes
    )
    context.completedStages.add(stage)

    // 2. Create a placeholder ReadRel that the consuming stage will use.
    placeholder = new ExchangeReadRel(
        exchangeInputId = stageId,
        outputSchema    = sourceFragment.outputSchema
    )

    // 3. Record the edge (will be linked to consuming stage ID later).
    pendingEdge = new PendingEdge(sourceStageId=stageId, spec=spec)
    context.pendingEdges.add(pendingEdge)

    return StageFragment(
        rootRel           = placeholder,
        outputSchema      = sourceFragment.outputSchema,
        partitioningInfo  = derivePartitioningAfterExchange(spec),
        partitioningInfo  = spec
    )
```

## 4. RelNode Plan Tree Surgery

### 4.1 Concept

A Calcite plan is a tree of `RelNode` (relation) nodes. Splitting the plan at an exchange boundary means:

1. **Cutting the tree**: the subtree rooted at the source side of the exchange is extracted and becomes the fragment for the upstream stage. `SqlProducer.toSql()` generates the SQL for this sub-tree.
2. **Inserting a placeholder**: where the cut was made, a synthetic `LogicalTableScan` referencing a shuffle input table (e.g., `shuffle_input_0`) is inserted into the downstream stage's RelNode sub-tree. The worker registers this table name as a DataFusion table provider backed by the exchange buffer.
3. **Schema preservation**: the placeholder `LogicalTableScan` carries the exact output schema (via `RelDataType`) of the stage it replaced, so the downstream plan remains type-correct.

### 4.2 Shuffle Input Table References

In the SQL-first approach, exchange inputs are represented as named tables in the generated SQL:

```sql
-- Stage-3 SQL references shuffle inputs from Stage-1 and Stage-2:
SELECT o.order_id, l.quantity
FROM shuffle_input_0 AS o        -- reads exchange output from Stage-1
JOIN shuffle_input_1 AS l        -- reads exchange output from Stage-2
ON o.order_id = l.order_id
```

Before executing a stage's SQL, the DataFusion worker registers each `shuffle_input_N` as a table provider backed by the Arrow Flight exchange buffer for the corresponding upstream stage and partition. The `ExchangeSpec` metadata in the `Stage` object tells the worker which upstream stage maps to each shuffle input table name.

### 4.3 Cutting Algorithm (Detailed)

```
function cutAtBoundary(rel, stageId) -> (sql, shuffleInputMapping):

    // Walk rel tree and find all placeholder LogicalTableScan nodes
    // inserted by walkBottomUp. These reference shuffle_input_N tables.
    shuffleInputs = findAllShuffleInputScans(rel)

    // Build mapping: shuffle_input_0 -> Stage-1, shuffle_input_1 -> Stage-2, etc.
    shuffleInputMapping = {}
    for i, scan in enumerate(shuffleInputs):
        shuffleInputMapping["shuffle_input_" + i] = scan.upstreamStageId

    // Generate SQL from the RelNode sub-tree (which now has placeholder scans).
    sql = SqlProducer.toSql(rel)
    return (sql, shuffleInputMapping)
```

Because `insertExchange` operates in-place during the bottom-up walk, no separate "cut" pass is needed. By the time `buildDAG` is called, each stage's `rootRel` already contains placeholder `LogicalTableScan` leaves in place of upstream subtrees.

### 4.4 Stage Fragment Self-Containment Rules

Each stage fragment must satisfy the following for independent execution:

| Requirement | How It Is Met |
|---|---|
| All table references are fully qualified | SQL uses fully-qualified table names resolved by the planner |
| No dangling references to relations from other stages | Cut points replaced by `shuffle_input_N` placeholder table scans |
| Schema of every node is fully typed | Schema propagated during walkBottomUp; placeholders carry upstream schema via `RelDataType` |
| All function references are resolved | SQL uses standard SQL function syntax; custom UDFs registered by name on DataFusion workers |
| All literal / type references are self-contained | SQL literals are value-typed; no cross-plan references exist |

### 4.5 Stage SQL Generation

```java
String buildStageSql(RelNode stageRoot) {
    // Use SqlProducer (wrapping UnifiedQueryTranspiler) to convert the
    // stage's RelNode sub-tree into a SQL string for DataFusion.
    SqlProducer sqlProducer = new SqlProducer(new DataFusionDialect());
    return sqlProducer.toSql(stageRoot);
}
```

The generated SQL is a self-contained query string. Shuffle input references appear as table names (`shuffle_input_0`, etc.) that DataFusion workers register as table providers before executing.

## 5. Partial Aggregation Optimization

### 5.1 Motivation

When a grouped `AggregateRel` (GROUP BY) is encountered, a naïve approach would:
1. Shuffle all raw rows to the correct partition (on grouping key hash).
2. Run the full aggregate on each partition.

This is wasteful because it shuffles every input row across the network before any reduction. The partial aggregation optimization pre-aggregates locally (per scan task), reducing the data volume before the shuffle.

### 5.2 Two-Phase Aggregation

For an aggregate `AGG(expr) GROUP BY k1, k2`:

**Phase 1 — Partial Aggregate** (runs in the producer stage, before the exchange):
- Computes partial results per local partition.
- For `SUM(x)`: emits partial sums per `(k1, k2)` group.
- For `COUNT(*)`: emits partial counts.
- For `AVG(x)`: emits `(SUM(x), COUNT(x))` as two columns (not a single AVG yet).
- For `COUNT DISTINCT`: cannot be fully pre-aggregated; falls back to sketch-based (HLL) or no partial agg.

**Phase 2 — Final Aggregate** (runs in the consumer stage, after the exchange):
- Merges partial results from all upstream partitions.
- For `SUM`: sums the partial sums.
- For `COUNT`: sums the partial counts.
- For `AVG`: computes `total_sum / total_count`.

### 5.3 SQL Representation of Partial Aggregation

Since SQL has no native concept of aggregation phases, the Stage Splitter manually decomposes aggregations into two SQL stages:

**Partial stage SQL** (runs before the exchange):
```sql
-- Partial aggregation: pre-aggregate locally before shuffle
SELECT k1, k2, SUM(x) AS partial_sum, COUNT(x) AS partial_count
FROM source_table
GROUP BY k1, k2
```

**Final stage SQL** (runs after the exchange):
```sql
-- Final aggregation: merge partial results from all partitions
SELECT k1, k2, SUM(partial_sum) AS total_sum, SUM(partial_count) AS total_count
FROM shuffle_input_0
GROUP BY k1, k2
```

The decomposition rules for each aggregate function:
| Original | Partial Stage | Final Stage |
|---|---|---|
| `SUM(x)` | `SUM(x) AS partial_sum` | `SUM(partial_sum)` |
| `COUNT(x)` | `COUNT(x) AS partial_count` | `SUM(partial_count)` |
| `COUNT(*)` | `COUNT(*) AS partial_count` | `SUM(partial_count)` |
| `AVG(x)` | `SUM(x) AS sum_x, COUNT(x) AS count_x` | `SUM(sum_x) / SUM(count_x)` |
| `MIN(x)` | `MIN(x) AS partial_min` | `MIN(partial_min)` |
| `MAX(x)` | `MAX(x) AS partial_max` | `MAX(partial_max)` |

> **Note:** With a future Substrait path, the `AggregationPhase` enum would provide native support for partial aggregation phases, avoiding the manual SQL decomposition above.

### 5.4 Pseudocode

```
function buildPartialAggregate(aggRel, inputRel) -> AggregateRel:
    partialMeasures = []
    for each measure in aggRel.measures:
        partialMeasures.add(measure.withPhase(INITIAL_TO_INTERMEDIATE))
    return AggregateRel(
        input    = inputRel,
        groupings= aggRel.groupings,
        measures = partialMeasures
    )

function buildFinalAggregate(aggRel, placeholderRel) -> AggregateRel:
    finalMeasures = []
    for each measure in aggRel.measures:
        finalMeasures.add(measure.withPhase(INTERMEDIATE_TO_RESULT))
    return AggregateRel(
        input    = placeholderRel,
        groupings= aggRel.groupings,
        measures = finalMeasures
    )
```

### 5.5 When NOT to Apply Partial Aggregation

| Condition | Reason |
|---|---|
| Global aggregate (no GROUP BY) + small table | GATHER is cheap; partial agg adds overhead for tiny datasets |
| `COUNT DISTINCT` without HLL support | Partial deduplication is not associative; skip unless HLL sketches are available |
| GATHER exchange is chosen anyway | A single downstream worker would receive all rows anyway; partial agg still helps reduce network bytes |

## 6. Cost Estimation for Exchange Strategy

### 6.1 Estimating Intermediate Cardinalities

The splitter maintains a `CardinalityEstimator` that propagates row count and byte estimates bottom-up through the plan:

```java
interface CardinalityEstimator {
    long estimateRows(RelNode rel, CatalogStats stats);
    long estimateBytes(RelNode rel, CatalogStats stats);
}
```

Base cases:

| Relation | Row Count | Bytes |
|---|---|---|
| `LogicalTableScan` | `stats.getTableRowCount(table)` | `stats.getTableSizeBytes(table)` |
| `LogicalFilter` | `childRows * selectivity` | proportional |
| `LogicalProject` | same as child | `childBytes * projectionWidthRatio` |
| `LogicalAggregate` | `min(childRows, NDV(groupingKeys))` | proportional |
| `LogicalJoin` | `leftRows * rightRows / max(NDV(leftKey), NDV(rightKey))` | proportional |
| `LogicalSort` (LIMIT N) | `min(childRows, N)` | proportional |

NDV for join keys is retrieved via `stats.getColumnDistinctCount(table, column)`.

### 6.2 Broadcast vs. Hash Join Decision

```
broadcastThreshold = 10 * 1024 * 1024   // 10 MB (configurable)

estimatedBuildBytes = estimateBytes(buildSide, stats)

if estimatedBuildBytes <= broadcastThreshold:
    use BROADCAST exchange on build side
else:
    use HASH exchange on both sides
```

The threshold is tunable via `splitter.broadcast.threshold.bytes` in the engine configuration. A larger threshold favors broadcast joins (less shuffle traffic) at the cost of more memory per worker holding the broadcast table.

### 6.3 Cost Model for Hash vs. Broadcast

The cost comparison (in abstract units proportional to bytes transferred):

```
cost(HASH_JOIN)      = leftBytes + rightBytes          // shuffle both sides
cost(BROADCAST_JOIN) = rightBytes * workerCount        // replicate build side

choose BROADCAST if rightBytes * workerCount < leftBytes + rightBytes
                 i.e., rightBytes * (workerCount - 1) < leftBytes
```

When `CatalogStats` returns `-1` (unknown), the splitter defaults to HASH exchange (conservative: avoids potentially blowing memory with an unexpectedly large broadcast).

### 6.4 Partition Count Selection

The number of hash partitions is set to `context.workerCount` (the number of available worker nodes for the consumer stage). The scheduler may later sub-divide partitions into tasks if a single partition is estimated to exceed the per-task memory limit.

## 7. Worked Example: 3-Table Join Query

### 7.1 Query

```sql
SELECT
    o.order_id,
    c.customer_name,
    SUM(l.quantity) AS total_qty
FROM
    orders   o
    JOIN customers c ON o.customer_id = c.customer_id
    JOIN lineitems  l ON o.order_id    = l.order_id
GROUP BY
    o.order_id, c.customer_name
ORDER BY
    total_qty DESC
LIMIT 10;
```

**Assumed table sizes:**
- `orders`: 500 MB, 5 M rows
- `customers`: 8 MB, 100 K rows  ← small enough to broadcast
- `lineitems`: 2 GB, 30 M rows

**Worker count**: 4

### 7.2 Calcite RelNode Tree (Before Splitting)

```
LogicalSort(limit=10, sort=total_qty DESC)
  LogicalAggregate(GROUP BY order_id, customer_name; SUM(quantity))
    LogicalJoin(o.order_id = l.order_id)
      LogicalJoin(o.customer_id = c.customer_id)
        LogicalTableScan(orders)
        LogicalTableScan(customers)
      LogicalTableScan(lineitems)
```

### 7.3 Bottom-Up Walk

**Step 1 — LogicalTableScan(orders)**
- Leaf node. Returns `StageFragment(LogicalTableScan(orders), UNPARTITIONED)`.

**Step 2 — LogicalTableScan(customers)**
- Leaf node. `estimatedBytes = 8 MB < 10 MB threshold`. Returns `StageFragment(LogicalTableScan(customers), UNPARTITIONED)`.

**Step 3 — LogicalJoin(o.customer_id = c.customer_id)**
- Left: orders (500 MB), Right: customers (8 MB).
- `8 MB <= 10 MB threshold` → BROADCAST the customers side.
- `insertExchange(customers_fragment, BROADCAST, numPartitions=4)` → seals **Stage-0** (scan customers).
- JoinRel left input = ReadRel(orders) (no exchange; probe side stays local to scan tasks).

  Wait — the orders scan is local to each task; for the broadcast join to work, the orders scan must be distributed. The splitter leaves the probe-side (orders) as-is. Stage-1 will be the join + orders scan; each task of Stage-1 broadcasts Stage-0 into memory and probes orders rows.

- Returns `StageFragment(Join(LogicalTableScan(orders), ShuffleInputScan(Stage-0)), UNPARTITIONED)`.

**Step 4 — LogicalTableScan(lineitems)**
- Leaf node. Returns `StageFragment(LogicalTableScan(lineitems), UNPARTITIONED)`.

**Step 5 — LogicalJoin(o.order_id = l.order_id)**
- Left: Join+Orders result (estimatedRows ≈ 5 M, estimatedBytes ≈ 500 MB).
- Right: lineitems (2 GB).
- Neither side is below 10 MB → HASH join.
- Left join key: `order_id` at column index 0 (in Join output schema).
- Right join key: `order_id` at column index 0 (in lineitems schema).
- Left is already UNPARTITIONED → need exchange. `insertExchange(left_fragment, HASH([0], numPartitions=4))` → seals **Stage-1** (orders scan + broadcast join with customers).
- Right is also UNPARTITIONED → `insertExchange(lineitems_fragment, HASH([0], numPartitions=4))` → seals **Stage-2** (lineitems scan).
- Returns `StageFragment(Join(ShuffleInputScan(Stage-1), ShuffleInputScan(Stage-2)), HASH_ON([order_id]))`.

**Step 6 — LogicalAggregate(GROUP BY order_id, customer_name; SUM(quantity))**
- Grouping keys: `order_id` (index 0), `customer_name` (index 1).
- Current partitioning: `HASH_ON([order_id])` from Step 5.
- Required partitioning for GROUP BY: `HASH_ON([order_id, customer_name])`.
- `[order_id]` ≠ `[order_id, customer_name]` → exchange needed.
- Apply partial aggregation:
  - Partial agg runs in Stage-3 (the 2nd join stage): `GROUP BY order_id, customer_name; SUM_PARTIAL(quantity)`.
  - `insertExchange(join_fragment_with_partial_agg, HASH([0,1], numPartitions=4))` → seals **Stage-3** (hash join + partial agg).
- Final agg runs in consumer: `GROUP BY order_id, customer_name; SUM_FINAL(partial_sum)`.
- Returns `StageFragment(FinalAgg(ShuffleInputScan(Stage-3)), HASH_ON([0,1]))`.

**Step 7 — LogicalSort(total_qty DESC, LIMIT 10)**
- Parent is FetchRel → need global top-10 → GATHER exchange.
- `insertExchange(agg_fragment, GATHER, numPartitions=1)` → seals **Stage-4** (final aggregation).
- Sort + Limit runs in the consumer stage on a single worker.
- Returns `StageFragment(Sort(ShuffleInputScan(Stage-4), LIMIT 10), SINGLE_PARTITION)`.

**Step 8 — buildDAG**
- Root stage = **Stage-5** (sort + limit).
- All stages are sealed. Build edges from pending edge records.

### 7.4 Resulting DAG

```
Stage-0: SCAN customers
         outputExchange: BROADCAST(numPartitions=4)
         estimatedBytes: 8 MB

Stage-1: SCAN orders + BROADCAST JOIN (Stage-0 as build side)
         + PARTIAL AGG (GROUP BY order_id, customer_name; SUM_PARTIAL(quantity))
         inputExchanges: [BROADCAST from Stage-0]
         outputExchange: HASH([order_id=0, customer_name=1], numPartitions=4)
         estimatedRows: ~5 M (post-partial-agg, reduced)

Stage-2: SCAN lineitems
         outputExchange: HASH([order_id=0], numPartitions=4)
         estimatedRows: 30 M

Stage-3: HASH JOIN (Stage-1 left, Stage-2 right on order_id)
         + PARTIAL AGG (continuation — but full agg here since we already partially aggregated)
         NOTE: In this example Stage-1 already applied partial agg before the exchange,
               so Stage-3 runs the FINAL agg after receiving the shuffled partial aggregates.
         inputExchanges: [HASH from Stage-1, HASH from Stage-2]
         outputExchange: GATHER(numPartitions=1)
         estimatedRows: ~5 M

Stage-4: FINAL AGG (SUM_FINAL, GROUP BY order_id, customer_name) [runs on single worker]
         inputExchanges: [GATHER from Stage-3]
         outputExchange: null (root stage)
         + SORT(total_qty DESC) + FETCH(LIMIT 10)
         estimatedRows: 10
```

### 7.5 DAG Topology Diagram

```
Stage-0 (scan customers)
    |  BROADCAST
    v
Stage-1 (scan orders + broadcast join + partial agg)
    |  HASH([order_id, customer_name])
    v
Stage-3 (hash join + final agg)  <---  Stage-2 (scan lineitems)  [HASH([order_id])]
    |  GATHER
    v
Stage-4 (sort + limit 10)  [ROOT]
```

### 7.6 Topological Order

`[Stage-0, Stage-2, Stage-1, Stage-3, Stage-4]`

- Stage-0 and Stage-2 have no dependencies (leaf scans); they can run in parallel.
- Stage-1 depends on Stage-0 (needs the broadcast table loaded before reading orders).
- Stage-3 depends on Stage-1 and Stage-2.
- Stage-4 depends on Stage-3.

## 8. Edge Cases

### 8.1 Subqueries (Scalar and EXISTS/IN)

Calcite represents correlated subqueries as `LogicalCorrelate` or within scalar expressions via `RexSubQuery`. The splitter handles them as follows:

**Uncorrelated scalar subquery**: Treated as a separate independent plan. The splitter recursively calls `split()` on the subquery plan, producing a sub-DAG. The scalar value is materialized first (Stage type: `SCALAR_SUBQUERY`), then broadcast as a literal to the outer query. The outer query stage adds a dependency on the scalar subquery stage.

**IN / EXISTS subquery (semi-join)**: The planner should have decorrelated these into `JoinRel` (semi-join type) before reaching the splitter. If not decorrelated, the splitter raises `StageSplitterException("Correlated subquery not decorrelated")`. Decorrelation is a planner responsibility.

**Lateral join**: Treated as a nested-loop join; the right side is re-evaluated per left row, which is only feasible if the right side is small (planner should already have enforced this). The splitter inserts no exchange; both sides execute within the same stage.

### 8.2 Common Table Expressions (CTEs)

Calcite inlines CTEs during optimization, but if the planner preserves multi-reference CTEs as shared `RelNode` sub-trees, the splitter handles them:

1. The splitter detects shared sub-trees (same `RelNode` instance referenced by multiple parents).
2. The shared sub-plan is split independently into a sub-DAG and materialized as an intermediate stage with its output written to a temporary exchange buffer.
3. Every reference becomes a `shuffle_input_N` table scan pointing to the same materialized CTE stage, with `BROADCAST` or `ROUND_ROBIN` depending on downstream usage.
4. If a CTE is referenced only once, it is inlined (the sub-tree is substituted directly) and the CTE stage is elided.

### 8.3 Window Functions

`LogicalWindow` (Calcite) requires data to be partitioned on the `PARTITION BY` keys and sorted on the `ORDER BY` keys within each partition. The splitter:

1. Inserts a `HASH` exchange on the `PARTITION BY` column indices before the `WindowRel`.
2. Each worker receives all rows for its assigned partitions and sorts locally.
3. If there is no `PARTITION BY` (global window), inserts a `GATHER` exchange so all rows reach one worker.
4. If the data is already partitioned on the `PARTITION BY` keys (from a prior exchange), the exchange is suppressed.

```
function handleWindow(windowRel, childFragment, context) -> StageFragment:
    partitionKeys = windowRel.partitionByKeys  // column indices

    if partitionKeys is empty:
        spec = ExchangeSpec(GATHER, [], 1, 0)
    else if childFragment.partitioningInfo == HASH_ON(partitionKeys):
        // No exchange needed.
        windowRel.input = childFragment.rootRel
        return StageFragment(windowRel, childFragment.partitioningInfo)
    else:
        spec = ExchangeSpec(HASH, partitionKeys, context.workerCount, 0)

    exchanged = insertExchange(childFragment, spec, context)
    windowRel.input = exchanged.placeholderReadRel
    return StageFragment(windowRel, partitioningInfo=derivePartitioningAfterExchange(spec))
```

### 8.4 UNION (ALL and DISTINCT)

Covered in Section 3.7. Additional edge cases:

**UNION ALL with incompatible parallelism**: If one branch of a UNION ALL comes from a single-partition GATHER stage, the splitter re-distributes it via ROUND_ROBIN before merging into the UNION consumer stage. This avoids a single-node bottleneck.

**Nested UNION**: The tree walk handles nested `SetRel` nodes naturally since each is visited bottom-up. Each inner UNION ALL adds a ROUND_ROBIN exchange boundary; a smart optimization (not required in v1) would collapse adjacent ROUND_ROBIN exchanges.

**UNION with ORDER BY**: SQL's `UNION ... ORDER BY` applies ordering to the combined result. The planner wraps the entire SetRel in a SortRel. The splitter processes the SortRel with a GATHER exchange (Section 3.6), collecting all UNION output onto one worker for the final sort.

### 8.5 Cross Join (Cartesian Product)

`JoinRel` with no join condition produces a cross join. The splitter:
- If either side is small (below broadcast threshold): BROADCAST the small side.
- Otherwise: treats both sides as if the join key is a constant (`1 = 1`), which causes all rows to hash to the same value → effectively a GATHER on one side, then a nested-loop join. This is flagged with a warning log: `WARN: Cross join between large tables; consider adding a join predicate`.

### 8.6 Multiple Outputs / Fan-Out

Some plans have stages whose output is consumed by more than one downstream stage (e.g., a CTE used twice, or a scan result reused in two branches of a UNION). The `ExecutionDAG` supports this: a single stage can appear as `sourceStageId` in multiple `ExchangeEdge` objects. The scheduler materializes the stage output once and serves it to all consumers.

### 8.7 Empty Plan / Single-Node Plan

If the plan consists of a single `ReadRel` with no transformations, the DAG contains a single leaf stage with no exchanges. This is valid and handled without special-casing; the `getTopologicalOrder()` returns a list of one stage and `getDependencies(stageId)` returns an empty list.

## 9. Pipeline Context: Logical vs Physical Planning

### 9.1 Where the Stage Splitter Fits

The Stage Splitter sits at the boundary between **logical planning** (what to compute) and **distributed execution** (where to compute it). Understanding this boundary is essential for reasoning about what the splitter is responsible for — and what it deliberately leaves to others.

```
SQL / PPL
    |
    v
UnifiedQueryPlanner
    |
    v
Calcite RelNode  (logical relational algebra)
    |
    v
Calcite RelNode (logical)  ← Stage Splitter input
    |
    v
[Stage Splitter]  ← inserts exchange boundaries; produces distributed physical topology
    |
    v
ExecutionDAG of per-stage SQL strings (generated by SqlProducer)
    |
    v
Distributed Scheduler  ← dispatches each stage's SQL to DataFusion workers
    |
    v
DataFusion (per worker)  ← parses SQL via SessionContext::sql(), optimizes, executes
    |
    v
RecordBatch stream  ← query results
```

### 9.2 Logical Plans All the Way Down (Until DataFusion)

The Stage Splitter operates **entirely on logical Calcite RelNode trees**. The input plan encodes *what* to compute — projections, filters, joins, aggregations — using standard relational operators. It contains no choices of join algorithm, parallelism degree, memory layout, or scan strategy.

After splitting, each stage's RelNode sub-tree is converted to a **SQL string** via `SqlProducer`. The splitter does not produce physical representations; it simply draws boundaries between stages and generates SQL for each. Each SQL string describes the same relational semantics as the sub-tree it was generated from, with upstream exchange inputs represented as `shuffle_input_N` table references.

The splitter's only "physical" decision is **where data moves between machines**: which exchange type (HASH, BROADCAST, GATHER, ROUND_ROBIN), on which key columns, and into how many partitions. This is the *distributed physical plan* — a topology of stages and shuffles — but the operators within each stage remain logical.

### 9.3 DataFusion's Role: Local Physical Planning

When a stage's SQL string arrives at a DataFusion worker, DataFusion parses the SQL and independently translates it into a local physical plan. This is visible in `query_executor.rs`:

```rust
// Parse SQL → logical plan → physical plan → stream
let dataframe = ctx.sql(&sql_string).await?;
let physical_plan = dataframe.create_physical_plan().await?;
```

The call to `create_physical_plan()` is where DataFusion makes all local execution decisions:

| Decision | Owner |
|---|---|
| Join algorithm (hash join, merge join, nested-loop) | DataFusion |
| Predicate pushdown into Parquet row-group filters | DataFusion |
| Projection pushdown (reading only needed columns) | DataFusion |
| Join reordering within the stage | DataFusion |
| Intra-stage parallelism (`target_partitions`) | DataFusion session config |
| Memory buffer sizing and spill strategy | DataFusion runtime env |
| Batch size for vectorized execution | DataFusion session config |

The coordinator (Stage Splitter + Scheduler) has **no visibility into or control over** these local decisions. DataFusion receives a logical fragment and optimizes it independently for the hardware and data it sees at runtime.

### 9.4 Separation of Concerns

| Concern | Owner | Where It Happens |
|---|---|---|
| WHERE data moves across machines (exchange boundaries, shuffle type, hash keys) | Stage Splitter | Coordinator, at plan time |
| HOW many stages exist and in what DAG topology | Stage Splitter | Coordinator, at plan time |
| HOW operators execute locally (algorithms, parallelism, memory) | DataFusion | Each worker, at execution time |
| WHICH files a scan reads (shard assignment) | Distributed Scheduler | Coordinator, at dispatch time |

This separation is intentional and valuable:

- **The coordinator stays engine-agnostic.** The Stage Splitter reasons over Calcite RelNode trees and produces SQL strings. Swapping DataFusion for a different SQL-capable execution engine would only require adjusting the SQL dialect in `SqlProducer`.
- **Workers optimize for local conditions.** DataFusion can exploit runtime statistics, hardware topology, and per-partition data characteristics that are unavailable to the coordinator at plan time.
- **SQL strings are portable and inspectable.** Stage SQL can be logged, replayed, and tested independently. Engineers can paste stage SQL directly into DataFusion CLI for debugging.

### 9.5 Comparison: Trino and Spark

Understanding how other distributed query engines handle this split illuminates the design choices made here.

#### Trino (formerly PrestoSQL) — Centralized Physical Planning

Trino performs **full physical planning centrally** on the coordinator before any work reaches workers. The coordinator produces a complete physical plan — including operator implementations, pipeline splits, and task layouts — and sends physical task descriptors to workers. Workers execute opaque tasks but have no planning autonomy.

**Consequences:**
- The coordinator must model every worker's hardware and data layout to plan effectively.
- Changing the execution model (e.g., adding a new join algorithm) requires coordinator changes.
- Workers are simpler but less adaptive to runtime conditions.

This engine does the opposite: the coordinator produces logical stage fragments (portable, engine-agnostic), and each DataFusion worker plans locally.

#### Spark — Stage-Based Separation (Most Similar)

Spark's architecture is the closest analogue. Spark's **DAGScheduler** decides the stage topology and shuffle boundaries (analogous to the Stage Splitter), producing a DAG of `ShuffleMapStage` and `ResultStage` objects. Within each stage, Spark's **task scheduler** sends closures (serialized Scala/Java code) to executors, which apply their own execution model.

**Key similarities to this system:**
- Stage boundaries are determined centrally by the coordinator.
- Each stage is an independent unit dispatched to workers.
- Workers execute each stage without further coordination.

**Key differences:**
- Spark stages carry serialized JVM bytecode (physical + implementation), not a portable logical plan. This system uses SQL strings as the portable intermediate representation.
- Spark's Adaptive Query Execution (AQE) re-plans exchange strategies at runtime based on shuffle statistics. This system currently plans exchanges statically using `CatalogStats`; runtime re-planning (analogous to AQE) is a potential future enhancement.
- DataFusion workers in this system independently re-optimize the logical fragment using their own rule-based and cost-based optimizer passes, a degree of local autonomy that Spark executors do not have (Spark executors run pre-compiled tasks without local re-optimization).

#### Summary

| System | Who decides exchange boundaries | What workers receive | Local re-optimization |
|---|---|---|---|
| **This system** | Stage Splitter (coordinator) | SQL string (per-stage) | Yes — DataFusion parses SQL and plans locally |
| **Trino** | Coordinator (full physical plan) | Physical task descriptor | No — workers execute as instructed |
| **Spark** | DAGScheduler (coordinator) | Serialized JVM closure | No — executors run pre-compiled tasks |
